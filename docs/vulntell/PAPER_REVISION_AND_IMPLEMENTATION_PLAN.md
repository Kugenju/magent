# 论文修改与 VulnTell 实施计划

## 1. 文档目的

本文档把《情报源评估》论文的修改目标、审稿意见回应、VulnTell 实施顺序和验收门禁放在同一份基线中。论文结果必须能够由版本化数据、代码和报告重新生成；系统实现中的字段和指标命名应与论文保持一致。

当前工作基础是六个来源的真实 COSV 批次：NVD、CISA KEV、Red Hat、Ubuntu、MSRC 和 OSV。当前基线位于 `deliveries/live-final-3`，统一窗口为 UTC `2026-08-11` 至 `2026-09-10`，记录数分别为 100、38、100、10、100 和 3。NVD、Red Hat、MSRC 的数量均为 100，必须先确认是否触及采集器单批上限；在确认分页完整性之前，不把这些数量解释为来源的真实规模或覆盖率。

## 2. 论文研究故事

论文的研究对象从孤立的数据库比较扩展为漏洞情报生态中的两个层次：

```text
来源质量：Source -> Quality Profile
传播关系：Source -> Vulnerability -> Source
应用决策：Quality + Propagation -> Source Portfolio
```

核心论点是：漏洞情报源在生态中承担不同功能，来源选择不能只依据记录数量或单一总分。Q-SEPTET 用于评价来源自身的覆盖规模、时效性、完整性、可验证性、维护能力、相对首发能力和场景适配性；时序传播图用于分析同一漏洞在来源之间的出现顺序、引用关系和潜在传播路径；二者共同支持面向应急响应、漏洞管理和自动化分析的来源组合。

建议将研究问题调整为：

1. 六个来源在七个质量维度上有哪些差异？
2. 漏洞情报在来源之间呈现怎样的时间传播顺序、引用关系和来源角色？
3. 来源质量指标与传播网络位置之间有什么关系？
4. 结合来源质量和传播关系的来源组合是否优于单一来源或仅按数据量选源？

论文中使用“潜在传播路径”“观察到的时序传播关系”等表述。只有明确引用证据时才报告高置信传播边；仅由共享标识和时间先后得到的关系不能写成确定的因果传播。

## 3. 审稿意见到修改动作的映射

| 审稿问题 | 修改动作 | 系统证据 |
|---|---|---|
| 缺少用户视角 | 引入 `EvaluationProfile`，为应急响应、漏洞管理、自动化分析定义目标、权重和门槛 | profile 配置、来源组合报告 |
| 权重缺乏依据 | 默认报告七维向量和 Pareto 前沿；权重配置化并做敏感性分析 | 权重配置、敏感性实验 |
| 热力图高低含义不清 | 统一“分数越高越好”；同时报告原始值、归一化值和方向 | 指标规范、图表脚本 |
| 时间基准不明确 | 固定 `published_at`、`source_added_at`、`modified_at`、`observed_at` 的语义和优先级 | schema、时间字段审计 |
| 完整性被跨源合并虚增 | 来源级完整性只从原始 `SourceObservation` 计算 | `metrics_by_source`、隔离测试 |
| 可验证性定义含混 | 分离 URL 覆盖率、别名覆盖率、有效引用率和原始载荷可追溯率 | 指标证据对象 |
| 原创性定义过强 | 全文改为“相对首次观察率/相对首发能力”，报告可比较样本数 | 指标说明、限制章节 |
| 缺少 benchmark | 建立 100 条字段/去重标注和 30 条传播关系复核集 | Precision、Recall、F1、Kappa |
| 贡献和应用不足 | 增加传播网络、来源角色和来源组合实验 | 传播图、画像实验 |
| 外部有效性不足 | 说明六源、单窗口、抽样/截断、许可和生态偏差 | 数据与限制章节 |

## 4. 分阶段实施计划

### 阶段 0：冻结真实数据证据

**目标**：把六个真实来源批次变成可复核、可审计的数据基线。

**完成内容**：固定数据集版本、窗口、采集时间、来源版本和许可证；校验 manifest、JSONL 行数、SHA-256、COSV schema、时间范围、重复 ID 和敏感字段；标记每个来源为 `full`、`sampled` 或 `truncated`。

**验收标准**：六个批次均通过批次校验；manifest 数量与文件一致；所有记录通过 COSV 校验；时间使用 UTC 半开窗口；任何达到 100 条的来源都有明确的分页/截断结论；批次不含凭据和完整响应。

**测试方法**：运行批次与 COSV 单元测试；执行数据审计脚本；对每个批次重复计算哈希；抽样检查原始记录到 COSV 的映射。

**产物**：`REAL_DATA_BASELINE.md`、数据审计 JSON、六个批次的校验报告。

### 阶段 1：修正采集完整性和跨源可比性

**目标**：消除单批 100 条上限导致的静默截断，并明确不同来源的职责边界。

**完成内容**：支持完整分页或显式抽样；在 manifest 中记录 `collection_mode`、`page_count`、`truncated`、`total_available` 和 `filter_rule`；重采集六源统一窗口；保留真实低数量来源，不人为补齐；区分全量漏洞库、已利用漏洞目录和生态专用源。

**验收标准**：采集器不静默截断；分页、空页、重复页和失败重试行为可验证；重复请求结果稳定；合并无重复；窗口过滤准确；所有不完整结果在报告中显式标记。

**测试方法**：分页模拟测试、失败恢复测试、重复运行哈希比较、真实 live smoke test。

### 阶段 2：冻结 Q-SEPTET v2 评估契约

**目标**：把论文指标改造成来源级、证据化、画像驱动的可计算契约。

**完成内容**：新增 `EvaluationProfile`、`SourceMetricSnapshot` 和 `MetricEvidence`（或等价模型）；每个指标包含 `raw_value`、`normalized_score`、`denominator`、`evidence_count`、`confidence` 和 `status`；保留旧 `compute_metrics` 兼容；完整性和可验证性基于来源原始 observation；时效性采用 `source_added_at - published_at`；相对首发率标明范围和可比较样本数。

**验收标准**：每个指标有定义、输入字段、分母、缺失规则和方向；比例位于 `[0,1]`；样本不足返回 `insufficient_data`，不生成无依据排名；一个来源不能借助其他来源补齐字段；权重配置化并可做敏感性分析。

**测试方法**：空值/无效值/时间逆序/小样本测试；来源隔离测试；公式性质测试；权重敏感性测试；fixture、串行、并行和恢复回归测试。

### 阶段 3：实现来源级 Q-SEPTET v2

**目标**：VulnTell 同时输出全局指标和六个来源的独立质量画像。

**完成内容**：扩展 `MetricSnapshot` 为 `aggregate_metrics`、`metrics_by_source`、`profile` 和置信度信息；报告原始值、标准化值和分母；把一个月维护性明确为窗口内维护代理指标。

**验收标准**：六源均有来源级指标；OSV 的 3 条记录被标记低置信度/样本不足；旧 fixture 流程不回归；来源级结果可由输入 observation 重新计算。

**测试方法**：构造“来源 A 只有标题、来源 B 只有描述”的反例；构造同一 CVE 不同来源时间差；单源数据原创性边界测试；两次计算逐字段一致。

### 阶段 4：实现潜在传播路径分析

**目标**：基于共享漏洞标识、别名、引用和时间顺序构建可审计的来源传播图。

**完成内容**：新增 `PropagationEvent`、`PropagationGraph`；保存 CVE、上下游来源、时间、延迟、证据类型和置信度；优先使用明确引用，其次使用共享标识和时序；计算入度、出度、传播延迟、覆盖范围和中介中心性；识别首发型、骨干型、补充型、汇聚型和专业型来源。

**验收标准**：每条边可回溯到具体漏洞和来源记录；缺少标识或时间不生成边；明确引用边和时间推断边分开；至少 30 条真实候选边人工复核，目标准确率不低于 0.80；达不到目标时只报告候选关系。

**测试方法**：合成 A→B→C 时间线、并列时间、缺失时间、逆序和重复别名测试；真实样本人工复核；重复计算图哈希。

### 阶段 5：建立人工 benchmark

**目标**：为去重、字段质量和传播关系提供可复核真值。

**完成内容**：抽取 100 条字段/去重样本和 30 条跨源传播样本；两名标注者独立标注；固定标注版本、规则和冲突处理。

**验收标准**：标注规则文档化；Cohen's kappa 目标不低于 0.80；报告 Precision、Recall、F1、置信区间和样本数量；没有人工证据的结论不写成准确识别。

**测试方法**：自动结果与标注集比较；规则变更后重新运行 benchmark；保存 benchmark hash。

### 阶段 6：来源组合和用户画像实验

**目标**：把质量和传播结果转化为实际来源选择建议。

**完成内容**：定义应急响应、漏洞管理、自动化分析三个画像；比较单源、按数据量、按 Q-SEPTET、按 Q-SEPTET 加传播关系四种策略；指标包括覆盖率、字段完整率、引用可追溯率、响应延迟和画像命中率。

**验收标准**：不同画像产生可解释组合；权重小幅变化不会使结论完全失控；样本不足来源不强制排名；推荐能回溯到指标和传播证据。

**测试方法**：权重敏感性、阈值边界、禁排名、人工 benchmark 对比和重复运行稳定性测试。

### 阶段 7：论文重写与复现

**目标**：让论文所有结论都能由代码、数据和报告复现。

**完成内容**：重写引言、方法、实验、讨论和限制；加入传播网络和来源组合实验；统一六源、窗口、版本、记录数和术语；建立“结论—证据—数据文件—代码函数”矩阵。

**验收标准**：每条审稿意见有回应位置和证据；图表由脚本生成；所有主要结论有数据支持；全文不把相对首发率写成真实原创率，不把潜在路径写成因果事实，不把单窗口写成长期维护结论。

**测试方法**：LaTeX 编译、引用/图表检查、自动表格重生成、模拟审稿和 claim-evidence 审计。

### 阶段 8：最终回归与交付

**目标**：完成系统、数据、论文和复现实验的统一交付。

**验收标准**：全量测试通过；fixture、真实批次和传播分析均可运行；串行/并行/checkpoint 结果一致；部分来源失败仍可生成降级报告；报告包含数据、窗口、版本、来源状态、指标证据和传播图版本；新增业务逻辑位于 `apps/vulntell`，不污染 `magent` 核心。

**测试方法**：

```bash
python -m pytest
python -m mypy src/magent
python -m apps.vulntell --json
python -m benchmarks.cli --out benchmarks/out
```

真实网络 smoke test 单独运行，不纳入默认离线 CI。

## 5. 当前阶段的边界和风险

- 六个来源只有一个月窗口，维护性只能解释为窗口内代理指标；至少三个连续窗口后再讨论稳定性。
- 单批 100 条记录可能是采集上限而非真实总量，阶段 1 完成前不做绝对规模排名。
- OSV 当前只有 3 条记录，所有比例都应带分母和置信度。
- CISA KEV 是已利用漏洞目录，与全量漏洞库承担不同职责，应采用职责匹配的评价和组合分析。
- 公开数据只能支持观测到的时序关系；因果传播需要明确引用或外部证据。
- `benchmarks/quality.py` 仍需确认是否完全迁移到 `apps.vulntell`，避免论文评测使用旧兼容实现。

## 6. 开发策略

前 2—3 个阶段由一个平衡型编码子代理实现，采用 `gpt-5.6-terra`、medium 推理强度，原因是任务主要是 Python 领域模型、确定性指标和测试，所需能力与成本之间较平衡。主代理负责审查改动、维护本计划文档、运行回归测试和决定是否进入下一阶段。任何涉及 `magent` 通用执行语义的修改，都必须先增加框架级回归测试；来源字段和论文指标逻辑留在 `apps/vulntell`。

## 7. 当前执行状态

截至本版本，阶段 0—2 的第一轮实现已完成：

- 批次 manifest 增加分页、实际抓取数量、截断状态、下一游标和采集完成状态；采集器不再对原始记录静默执行 `raw[:100]` 截断。
- 新增 `EvaluationProfile`、`MetricEvidence` 和 `SourceMetricSnapshot`；来源级指标从原始 `SourceObservation` 计算，并保存分母、观测 ID、载荷哈希、质量问题数、置信度和状态。
- 来源级指标已经提供字段存在率、原始载荷可追溯率、时效延迟统计、引用 URL/有效引用统计和画像关键词匹配率；旧聚合报告契约和冻结 baseline 保持 v1 兼容。
- 新增来源隔离、指标证据、空来源和分页采集测试；针对性测试通过 23 项，批次/COSV/旧指标回归测试通过 65 项（含新增测试）。

阶段 0 的六源真实批次仍需重新运行完整分页采集并生成正式数据审计报告；阶段 3—8 尚未完成，不应在论文中提前使用传播图、长期维护结论或来源推荐结论。
